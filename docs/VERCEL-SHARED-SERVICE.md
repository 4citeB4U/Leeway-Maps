# Vercel shared services deployment adapter

Prepared code, not a deployed service. Set the Vercel project root to `apps/transit-world`, Node.js 24, and use the checked-in `vercel.json`. It builds the Vite frontend at `/` and serves the Node catch-all under `/api`. The function recognizes only `/api/peers/*` and `/api/hazard-reports[/status]`; existing local-only proxy providers are not automatically deployed. Use the frontend and these APIs on the same origin. Cross-origin CORS is not enabled. GitHub Pages remains static and cannot execute these handlers.

## Server-only environment

Configure these in Vercel environment settings, never with the `VITE_` prefix and never in a committed file:

- `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`: HTTPS Upstash REST endpoint and write-capable token. `KV_REST_API_URL` / `KV_REST_API_TOKEN` aliases also work. The token needs GET, SET, INCR, EXPIRE and EVAL access. Do not use a read-only token.
- `LEEWAY_REDIS_NAMESPACE`: required 1–80 character letters/digits/colon/underscore/hyphen namespace. Use distinct namespaces **and credentials/databases where possible** for production and preview. Never attach public untrusted PR previews to production secrets or state.
- `LEEWAY_PEER_SIGNALING_ENABLED=1`, `LEEWAY_PEER_SIGNING_SECRET` (at least32characters), `LEEWAY_PEER_USERS_JSON` (the provisioner account schema with salted password hashes, max128KiB). See `PRIVATE-PEER-COMMUNICATIONS.md`. Use Vercel sensitive environment values. Users JSON remains in the function environment; it is not saved in Redis or exposed to Vite.
- `LEEWAY_PEER_ICE_SERVERS`: optional authorized STUN/TURN configuration returned only after sign-in. TURN credentials returned to clients should be short-lived; this adapter does not operate a TURN server. Restrictive mobile networks still require TURN.
- `LEEWAY_HAZARD_REPORTS_ENABLED=1`, `LEEWAY_HAZARD_REPORTS_WRITE_TOKEN` (at least24characters) to enable shared hazard reporting. The client must present the operator-issued write token; no token is embedded in the public bundle.

Provisioning a paid service, adding secrets and deploying are separate operator actions. None is performed by this code. Missing/invalid Redis configuration returns503, including status; there is no per-instance in-memory fallback. Redis failure does not claim a successful broadcast. A network timeout after an atomic commit is necessarily an **unconfirmed** result: inspect state before repeating an invitation or report. No automatic HTTP-level mutation retry is performed.

## Consistency, retention and capacity

Each operation loads a fresh bounded snapshot and builds an isolated synchronous store. Mutations commit with a Redis Lua compare-and-set against the exact preceding snapshot; conflicts re-evaluate at most4times. A unique revision prevents stale overwrite. The success response is sent only after the atomic commit succeeds. Read-only directory/inbox/nearby operations use a coherent committed snapshot and prune expiration in memory without rewriting. Corrupt and oversized state fails closed rather than being discarded.

Two Redis state keys per namespace are each capped at1MiB. Peer state expires after1hour without a mutation, while individual presence/invitations/sessions/inbox events retain their shorter contract TTLs. Hazard state expires after121minutes without a write; individual reports expire after30–120minutes. Redis state survives function instance replacement; this is not permanent message history or a backup guarantee. Hazard reports cap at5000 (the byte cap can be reached earlier), results at100. Peer limits are200 peers/invites/sessions,200 inbox recipients,64events per inbox and512KiB overall inbox data. Under capacity pressure old signaling events can be evicted; clients must timeout/reinvite. WebRTC audio/video and text messages are not stored in this Redis adapter.

Distributed one-minute limits apply before handlers: peer requests3000global/240perIP, hazard600global/60perIP; login30global/5perIP; peer writes600global/120perIP; hazard writes100global/6perIP; invitations6perIP. Per-IP keys contain a SHA256 digest of Vercel's supplied IP and expire after60seconds. Process-local handler limits remain an additional conservative guard and may throttle sooner. Limits also apply to invalid credentials. The global guard runs first to bound creation of per-IP keys. Vercel's firewall and account spending controls must still protect against flood traffic: rejected requests still invoke a function and usually a Redis command.

Ordinary read:2rate-limit REST calls +1snapshot GET. Ordinary write:4rate-limit calls +2CAS calls on first success, up to8CAS calls under contention. Login adds2rate-limit calls; invitation adds1. Each Redis REST call has a3second timeout; request bodies are bounded32KiB peers/4KiB hazards. Function max duration is60seconds. Redis responses cap at2MiB. Snapshot GET and CAS retransmit up to1MiB, so this intentionally simple small-fleet adapter has bandwidth and contention costs; it is not an unlimited company-wide message bus. Redis billing can count commands executed inside Lua separately. Configure spend alerts/limits with the chosen plans and measure usage; no free-tier or dollar-cost promise is made.

## Qualification before production

Local automated tests cover independent handler instances, concurrent CAS conflict replay, persisted reports/directory, organization isolation, distributed login limits, malformed state, and missing storage. They use an in-memory implementation of the Redis command boundary, not a live Upstash database. Before rollout, run two independent deployed clients against a dedicated preview Redis namespace, check shared directory/report visibility after function cold starts, test simultaneous invitations, expiry, injected Redis failures, and physical phone-to-phone TURN-assisted audio/video. A successful static build does not qualify the deployed service or media transport.
